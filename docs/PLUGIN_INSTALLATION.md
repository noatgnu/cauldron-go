# Plugin Installation

Plugin system handles how custom data analysis pipelines might be used within Cauldron. Non-built-in plugins might be installed through the custom protocol `cauldron://install`, a fallback http port that can be enable in the settings or manually from a direct git url of the plugin repo.

## Built-in versus remote plugins

`PluginRegistry.InstallSource` is either `"builtin"` or `"remote"`.

Built-in plugins ship inside the app's own bundled `plugins/` directory. There is no manifest. `build.sh`'s `copy_resources()` copies every subdirectory under the repo's `plugins/` folder wholesale into the build output next to the compiled executable. A few plugins, `uniprot-fetcher`, `wide-to-long`, and `long-to-wide`, additionally get a prebuilt native binary copied in from `bin/external/<os>-<arch>/`.

Remote plugins are installed by the user via git, either from a plugin registry or a raw repository URL, and always get `InstallSource: "remote"` hardcoded by the installer, regardless of what the plugin's own `plugin.yaml` `repository:` field says.

A plugin folder that already exists on disk with no DB row yet, for example one manually dropped in, falls back to inferring its source from whether `plugin.yaml` sets `repository:`. Set means `remote`, unset means `builtin`.

To add a new built-in plugin during development, either hand-create `plugins/<id>/` following the schema in the [Plugin Developer Guide](PLUGIN_DEVELOPER_GUIDE.md), or use `go run ./cmd/plugin-scaffolder` (see that guide's Getting Started section). As long as the plugin's `plugin.yaml` has no `repository:` field, it is classified `builtin` the first time the app loads it. Rebuild via `build.sh`, or copy the folder into a dev binary's `plugins/` directory and call `ReloadPluginsV2()`, to pick it up live.

## Installing via a custom protocol link: `cauldron://install`

This only works as a registered OS protocol on Windows.

The URL format is `cauldron://install?repo=<url>&ref=<branch|tag|commit>&registry=<registry-source-id>`. Only `repo` is required. `ref` and `registry` are optional.

On launch, or relaunch, with a `cauldron://` URL as a CLI argument, `App.Initialize` detects it, waits two seconds for the frontend to finish booting, then resolves it. It fetches the plugin's `plugin.yaml`, either via a temp clone or a clone-free path using GitHub's raw-content API for GitHub URLs, computes whether it needs Python or R, and emits a `plugin:install:request` Wails event with the plugin's metadata. This step only requests confirmation. It does not install anything itself.

The listener lives in `frontend/src/app/app.ts` (`setupPluginInstallationListeners`, kept at the app-root level since an install request can arrive on any page). It opens `ConfirmPluginInstallDialog` with the event payload. On confirm, if an SSH key was supplied, it is saved via `SaveGitAuthConfig` first, then `ConfirmPluginInstallationWithRegistry` (or `ConfirmPluginInstallation` when there is no registry source) triggers the install.

## Installing via a link, cross-platform: the HTTP fallback

For another path of installation via link but through a universal HTTP service, the app can starts a local HTTP server at `http://localhost:50060` (`HTTPInstallServer`, started in `App.Initialize` regardless of OS):

- `GET /install?repo=<url>` mirrors the same install-request flow and event emission as the protocol handler, though it only reads `repo`, not `ref` or `registry`.
- `GET /health` reports server health.
- `GET /` renders an HTML help page.

Autogenerated plugin READMEs intended to work cross-platform will have link to `http://localhost:50060/install?repo=...` rather than, or in addition to, a `cauldron://` link.

A confirm dialog will be shown within the application that require the user manual input to progress after clicking the installation through a link.

## Installing manually: "Install from Git"

The manual install dialog (`install-plugin-dialog`) has these fields:

- **Repository URL**, required, validated against `^(https?:\/\/|git@)[\w.-]+[:/][\w.-]+\/[\w.-]+(\.git)?$`. It accepts `https://github.com/user/repo`, `https://github.com/user/repo.git`, or `git@github.com:user/repo.git`.
- **Git Reference**, optional: a branch, tag, or commit hash. Leaving it empty means the default branch's HEAD.
- Under a collapsed "Advanced: Git Authentication" panel: **SSH Private Key Path**, chosen via a native file-picker "Browse" button, and **Passphrase**, optional, with a show and hide toggle, plus a "Validate Key" button that parses the key locally (`gossh.ParsePrivateKey` or `ParsePrivateKeyWithPassphrase`) without contacting the remote.

On submit, the caller (`plugins.ts` or `plugin-registry.ts`) opens a progress dialog that saves the SSH config, if given, then triggers the actual install.

## Git mechanics

`PluginInstaller.InstallPlugin` does a full clone then does the following:

- Checks out `ref` if given. It first tries `ref` as a commit hash, and falls back to treating it as a branch name if that fails. An empty `ref` leaves the default branch checked out.
- Places the plugin at `plugins/<pluginID>-<registryRowID>/`. The numeric DB row ID disambiguates multiple installs sharing a plugin ID.
- Sets `InstallSource: "remote"` unconditionally.
- Reads and YAML-unmarshals `plugin.yaml`, but does not run schema validation at install time. A malformed `plugin.yaml` fails later, silently, when the plugin loader next scans the directory via `LoadPlugins` or `ReloadPlugins`.
- Calls `ReloadPlugins()` to hot-reload the plugin set into the running app.
- Refuses to reinstall over an existing, working installation of the same repository. It checks that the folder exists and the plugin currently loads. If the existing install is broken, for example the folder is missing or fails to load, it cleans up the stale DB row and proceeds with a fresh install.
- If the plugin ships an optional `dependencies.json` (`PluginDependencyGraph`) at its root, on Linux and macOS a suggested `apt install` or `brew install` command for declared system packages is surfaced as message. Windows is explicitly skipped for this step.

`FetchPluginInfo`, used to preview a plugin before confirmation, and `CheckRepositoryUpdate` both use shallow clones with depth 1. Only the actual install does a full clone.

## Updating an installed plugin

`UpdatePlugin(repoURL)` and `UpdatePluginWithForce` open the existing local clone and check for a clean working tree. If the tree is dirty and the call is not forced, it returns an error string prefixed `LOCAL_MODIFICATIONS:`, which the frontend uses to offer a force option. If forced, it does a hard reset first. It then does a real `git pull` on whatever branch is currently checked out. It does not switch branches or tags. If the local folder is missing entirely, it falls back to a full reinstall.

`UpdatePluginToCommit(repoURL, commitHash)` and its forced variant use the same dirty-check and force-reset logic, then fetch and check out a specific commit rather than pulling the tracked branch. This is used for updating or downgrading to a specific version.

`ReinstallPlugin(repoURL)` deletes the existing plugin folder entirely and does a fresh full clone, checking out the previously recorded commit, not necessarily the latest one. This is a full nuke-and-reclone, not a `git pull`.

`CheckRepositoryUpdate(repoURL, currentCommit)` does a fresh shallow clone just to read the remote HEAD and compare it against `currentCommit`. It returns whether an update exists, plus a synthesized GitHub compare-URL changelog link that is only meaningful for GitHub-hosted repos.

App-level batch operations, `UpdateAllRemotePlugins`, `ForceUpdateAllRemotePlugins`, and `ForceUpdateRemotePlugin`, iterate every remote-installed plugin and apply the operations above. `SetPluginUpdatePolicy` (`"auto"` or `"manual"`) and `PinPluginVersion`/`UnpinPluginVersion` let a user opt a specific plugin out of update checks entirely.

If a plugin was installed through a plugin registry, meaning it has a `RegistrySource`, `CheckPluginUpdate` instead asks the registry's `check_update` API endpoint rather than doing its own shallow-clone comparison. See the registry client in `pkg/registry/client.go`.

## Uninstalling

`PluginInstaller.UninstallPlugin(repoURL, options)` always deletes environment bindings and custom env vars for the plugin. It optionally deletes its saved git auth config, job history including job output directories, and any bound Python venvs or R renvs. It then removes the plugin folder and its DB row, and reloads the plugin set.

## SSH key management

Auth is keyed by `GitAuthConfig` (table fields: `RepositoryURL` with a unique index, `SSHKeyPath`, `SSHKeyPassphrase`), looked up by normalized repository URL every time a clone, pull, or fetch happens. `GetAuthMethod` returns no error and no auth when no config exists for a URL, so public repos work with zero configuration.

Two places write to the same table:

1. Settings, then Git (`settings-git`) is a dedicated page listing existing configs. It lets you add one ahead of time (Repository URL, SSH Private Key Path via file picker, Passphrase, and a "Validate Key" button) or delete one.
2. Inline in an installation dialog: the "Advanced: Git Authentication" panel appears in both the manual install dialog and the protocol or registry confirm dialog. This is not transient. Whatever you enter is saved via the same `SaveGitAuthConfig` call before the install proceeds, so it becomes a standing config for that repository URL, visible afterward on the Settings, Git page, and reused automatically for future updates.

`normalizeRepoURL` rewrites SSH-shorthand URLs (`git@host:owner/repo`) to `ssh://host/owner/repo` before using them as the lookup key. An HTTPS clone URL for the same repository, such as `https://github.com/org/repo`, normalizes differently and will not match an SSH-keyed config. You need a separate `GitAuthConfig` entry for each URL form you use to install or update that repository, even though they point at the same remote.
